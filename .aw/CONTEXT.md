# Context

## Domain Language

| Term | Definition | Avoid |
| --- | --- | --- |
| **Session** | A configured working directory with associated workspaces and state. | Working Directory |
| **Workspace** | A visual layout instance belonging to a session, created from a template. | WorkspaceInstance |
| **Template** | A reusable layout definition. Workspaces reference a template but are not updated when the template changes. | Layout |
| **LayoutTree** | A recursive tree of splits and panels describing a workspace's visual arrangement. | Layout |
| **Command** | A discrete, serializable operation that mutates application state. | Action, Operation |
| **ExecutionOutcome** | Return type of a command: `{ result, events }` where `events` are `DomainEvent` variants. | |
| **DomainEvent** | A typed enum describing what changed during a command execution. The command layer produces them; Tauri and MCP translate them independently. | Event |
| **Repository** | A concrete struct (e.g. `SessionRepository`) holding a `&Connection` reference, providing typed query methods. No traits. | |
| **Database** | Holds `db_path: PathBuf`. Opens a fresh `rusqlite::Connection` per command. Exposes repository accessors (`db.sessions(&conn)`, etc.). | DB, Connection |
| **AppState** | Holds `Database` only. No mutexes. Cloned cheaply (PathBuf). | State |
| **Issue** | A tracked unit of work or report belonging to a Session, stored in the database; the AI creates them and the user views them. Ephemeral app state, never committed to the repo. | Task, Ticket |
| **Issue Tracker** | The panel type that displays a session's Issues in a GitHub-style list. | |
| **ChangeEvent** | A row in the `change_events` table recording an entity mutation (created, updated, deleted), written by a SQLite trigger. Contains the full entity snapshot as JSON so the frontend can animate changes even after the source row is gone. | Event, Notification |
| **CDC (Change Data Capture)** | The pattern of using database triggers to write mutation events into a queue table, decoupling data changes from their visual representation. | |
| **File Viewer Panel** | A panel type that displays file contents (markdown or code) with syntax highlighting. Each instance has its own tab state. | |
| **File Tree Panel** | A panel type that displays the session's working directory as a navigable tree. Clicking a file opens it in the last-focused File Viewer Panel. | |
| **Diff Viewer Panel** | A panel type that displays git diffs in a unified view with syntax highlighting. | |
| **Visual Canvas Panel** | A panel type that displays a 2D canvas with Nodes, Edges, Groups, and Tags for visual planning and connection mapping. | |
| **Content Fingerprint** | A hash of file content used as a cache key for syntax highlighting results, preventing redundant work when file content hasn't changed. | |
| **Visual Canvas** | A 2D canvas for visual planning and connection mapping, where humans and AI collaboratively place and arrange elements. | Canvas, Board, Whiteboard |
| **Node** | A generic visual entity on a Visual Canvas representing a concept, task, artifact, or idea. Has position (x, y) and content but no type constraints. | Element, Shape |
| **Edge** | A directional link between two Nodes representing a relationship (dependency, flow, association). Has source and target. | Connection, Link |
| **Group** | A named collection of Nodes on a Visual Canvas, defined by explicit `node_ids` membership. The UI handles spatial containment detection; the AI works with the membership list. | Cluster, Container |
| **Tag** | A simple string label attached to Nodes for categorization (e.g., "priority:high", "blocked"). No associated colors in v1. | Label, Category |
| **C4 Diagram** | A repo-scoped, persistable visualization of codebase architecture following the C4 model (Context, Container, Component, Code). Generated by the AI via MCP, keyed by `repo_path`. Goes stale as the codebase evolves; regenerated on demand. | Architecture Diagram, Code Map |
| **C4 Diagram Panel** | A panel type that renders a C4 Diagram with drill-down hierarchy. Has a zero state with a copy-paste prompt for the AI to generate a diagram. | |
| **C4 Level** | One of four abstraction layers in a C4 Diagram: Context (system + actors), Container (apps, DBs, services), Component (modules, packages), Code (classes, functions with inline snippets). | |
| **Code Intelligence Index** | Repo-scoped structural data extracted by tree-sitter/LSP: symbols, definitions, references, call graphs, import relationships, file structure. Incrementally updated via content fingerprints. | Symbol Index |
| **Code Intelligence Vector Store** | Repo-scoped semantic embeddings of code chunks (functions, classes, docstrings). Regenerated on demand, not incrementally. | Embedding Store |
| **Side Handle** | A half-pill interactive element on a node's border (top/right/bottom/left) that starts edge creation via press-and-drag. Rendered as an SVG `<path>` with an invisible hit-area `<rect>` behind it. Always present in the DOM; visibility controlled by CSS custom properties on the parent node `<g>`. | Connection point, port, anchor |
| **Handle State** | One of three visual states per handle: **hidden** (node not hovered, side unconnected), **bobbing** (node hovered, side unconnected — plays a side-specific bob keyframe animation), **still** (side is connected — full opacity, no animation). State is derived from `hoveredNodeId` in panel state + edge data from the canvas store. | |
| **Handle Hit Area** | An invisible SVG `<rect>` behind each visible handle, larger than the handle (10px bias outward, 2px toward node). Uses `fill="none" pointer-events: all` to capture mouse events. The visible handle has `pointer-events: none`. | |
| **Canvas Interaction Hover Tracking** | `hoveredNodeId` stored in panel-level React state (not in a dedicated hook). Set by `onMouseEnter`/`onMouseLeave` on each node `<motion.g>`. Drives handle visibility, bob/connected state, and future drop-target validation. | |
| **Git Graph Panel** | A panel type that visualizes git commit history as a DAG: branch lines, commit dots, merge forks, and ref labels on an SVG graph canvas column, with resizable author/message/date text columns. Follows the File Tree → File Viewer dispatch pattern: clicking a commit opens its diff in the Diff Viewer Panel. | Git Tree, commit list, history panel |
| **Git Graph Canvas** | The leftmost column showing the git DAG rendered in SVG: colored branch lines (`<path>`), commit dots (`<circle>`), and ref labels (pill-shaped `<rect>`+`<text>`). | Branch visualization, commit graph |
| **Lane** | A vertical track in the graph canvas where a single branch line runs. Assigned by the greedy column algorithm so branch lines don't overlap. Lanes are recycled once a branch segment terminates (its end row is reached). | Column, track |
| **Branch Line** | A colored SVG `<path>` connecting parent/child commit dots within a lane. Color is keyed deterministically by the logical branch identity (the commit SHA at the branch point), not by column. Colors cycle through 10 theme-compatible hues. | |
| **Ref Label** | A colored pill showing a branch name, tag, or remote-tracking branch name on the graph canvas. `tag: ` prefix is stripped from tag labels. HEAD indicator distinguishes the current branch with a distinct visual marker. | |
| **Commit Row** | One row in the virtualized commit list containing: graph canvas section + short hash + author + message + relative date. Rendered only when in the viewport via `@tanstack/react-virtual`. | |
| **Commit Detail Pane** | The bottom section of the Git Graph Panel showing metadata for the selected commit: full hash (copyable), author, date, full message, a file tree of changed files with additions/deletions per file, and a tree/flat view toggle with keyboard shortcut. Clicking a file dispatches its per-commit diff to the Diff Viewer Panel. Toggleable/resizable split from the graph list. | |
| **Commit Selection** | The set of selected commit rows in the Git Graph Panel. Single selection on click. Contiguous range selection via shift-click. Non-contiguous multi-select is not supported in v1. | |
| **Commit Quick-Open** | A modal invoked by `Cmd+Shift+O` that accepts a pasted SHA (or branch/tag name) to navigate to and select a specific commit in the Git Graph Panel. | |
| **Range Diff** | A unified diff spanning a contiguous commit selection (`git diff oldest^..newest`) shown in the Diff Viewer Panel as a single collapsed view, analogous to a PR's "files changed" tab. | |
| **Two-Phase Loading** | The data loading pattern where `get_graph_topology` returns SHA + parents + refs first (fast), then `get_commit_details` lazily fetches author/date/message via `git cat-file --batch` for visible viewport rows only. Matches Zed's architecture. | |
| **Greedy Column (Lane) Assignment** | The algorithm (ported from tig/CommitGraph) that assigns each commit to a vertical lane in the graph canvas by traversing the topology in topological order, handling branch-out, merge, and branch-collapse cases. Runs in TypeScript. | |

## Relationships

- A **Session** contains zero or more **Workspaces**.
- A **Session** contains zero or more **Issues**.
- A **Session** contains zero or more **Visual Canvases**.
- A **Workspace** references one **Template**.
- A **Template** is standalone; modifying it does not affect existing workspaces.
- A **Workspace** owns one **LayoutTree**.
- A **Database** owns one or more **Repositories**.
- An **AppState** owns one **Database**.
- A **Command** returns an **ExecutionOutcome** containing **DomainEvents**.
- A **C4 Diagram** belongs to a Repository (identified by `repo_path`), not a Session. Survives session deletion.
- A **C4 Diagram Panel** renders one **C4 Diagram** with drill-down through four **C4 Levels**.
- A **C4 Diagram** is generated by a hybrid process: tree-sitter extracts structural data (files, imports, call graphs), then the AI interprets and labels the semantic meaning.
- A **Code Intelligence Index** belongs to a Repository (identified by `repo_path`). Shared across sessions.
- A **Code Intelligence Vector Store** belongs to a Repository (identified by `repo_path`). Shared across sessions.
- A **Git Graph Panel** dispatches diffs to the **Diff Viewer Panel** (mirrors File Tree → File Viewer pattern): single commit → `git show`, contiguous range → `git diff oldest^..newest`.
- A **Commit Quick-Open** modal navigates within the **Git Graph Panel** to select a commit by SHA/branch/tag.

## Decisions

- Persistence: rusqlite (sync), see [ADR 0001](adr/0001-use-rusqlite-sync.md).
- Concrete repositories, no trait indirection.
- Workspaces normalized with `session_id` FK. Templates are optional metadata on workspaces.
- No migration from JSON. Start fresh.
- Issues are ephemeral app state stored in SQLite, never committed to the repo or working directory; see [ADR 0013](adr/0013-issue-tracker-storage.md).
- Issues attach to a Session via `session_id` FK with `ON DELETE CASCADE`, mirroring workspaces.
- An Issue has a per-Session sequential `number` (GitHub-style `#N`), a `title`, a markdown `body`, an `author` (`ai`/`user`), and `created_at`/`updated_at`.
- Issue lifecycle and triage are two independent axes: `state` (`open`/`closed`) and a `labels` JSON array (default `["needs-triage"]`).
- Default label vocabulary: `needs-triage`, `needs-info`, `ready-for-agent`, `ready-for-human`, `wontfix`; the AI may add ad-hoc labels.
- No comment thread in v1; the AI keeps the Issue `body` current as a living description. Comments (a separate `issue_comments` table) are a possible fast-follow.
- The Issue Tracker panel is read-only for the user; all Issue mutations flow through the AI via MCP. The panel reads via Tauri (`list_issues`, `get_issue`) and refreshes on the `issues-changed` event.
- UI animations for MCP-driven entity mutations (create, update, delete) are driven by a CDC event log rather than state diffing; see [ADR 0014](adr/0014-cdc-event-log-for-mcp-animations.md).
- Visual Canvas Panel is a new panel type alongside terminal, file-viewer, issue-tracker, etc.
- Visual Canvas data is independent from Issues; no cross-referencing in v1.
- Session owns Visual Canvases (one-to-many).
- Visual Canvas data persists in SQLite (like Issues), not in the working directory.
- Visual Canvas canvas is infinite (pan/zoom), not bounded.
- Visual Canvas uses CDC events for AI-driven mutations, ensuring responsive animations.
- Nodes, Edges, Groups have a generic `metadata: JSON` field for arbitrary key-value data.
- Tags are simple strings attached to Nodes only (not Edges or Groups).
- C4 Diagrams are the first repo-scoped entity — stored in a separate table keyed by `repo_path`, not `session_id`.
- Diagram management (list, delete, rename) is handled through the C4 Diagram Panel UI. Generation is the only MCP operation.
- C4 Diagram Panel renders with drill-down hierarchy: Context → Container → Component → Code.
- Code level (L4) displays inline code snippets within the panel.
- The MCP tool (`generate_c4_diagram`) accepts optional `scope` (path/module focus) and `max_depth` (1-4, defaults to 3).
- C4 Diagram generation is hybrid: tree-sitter/LSP for structural extraction, AI for semantic interpretation and labeling.
- The C4 Diagram Panel zero state shows a copy-paste prompt for the user to give to the AI.
- Code Intelligence Index is repo-scoped (keyed by `repo_path`), shared across sessions. Incrementally updated using content fingerprints — only changed files are re-indexed.
- Code Intelligence Vector Store is repo-scoped (keyed by `repo_path`), shared across sessions. Regenerated on demand, not incrementally (embedding computation is expensive).
- Staleness strategy: index auto-updates incrementally on tool invocation; vectors regenerate on demand when the user/AI requests it.
- v1 Code Intelligence MCP tools: structural search/navigation (tree-sitter + LSP), semantic search (vectors), history (git log, blame, diff), ownership (CODEOWNERS, git blame), C4 diagram generation.
- Deferred to v2+: cross-service linking, runtime traces, diagnostics, refactoring, infra-as-code, similarity detection, fresh docs.
- Git Graph Panel uses two-phase loading (topology first, details lazy) with TypeScript lane computation and SVG rendering; see [ADR 0016](adr/0016-git-graph-panel.md).
- Git Graph Panel → Diff Viewer dispatch mirrors the File Tree → File Viewer pattern: click opens in the last-focused Diff Viewer, single commit dispatches `git show`, contiguous range dispatches `git diff oldest^..newest`.
- Commit Detail Pane file tree uses tree view by default, with `Ctrl+T` toggling between tree and flat view (scoped to the detail pane). Clicking a file dispatches its per-commit diff to the Diff Viewer Panel.
- Branch colors are keyed by logical branch identity (the branch-point commit SHA), not by lane column. This keeps a branch's color consistent even when its lane changes across the graph.
- Lanes are recycled after a branch segment terminates (its end row is passed). The column becomes available for a new branch in subsequent rows.
- Commit Quick-Open (`Cmd+Shift+O`) is a command-palette modal that accepts a pasted SHA, branch name, or tag name. Live-matches against known refs and partial SHAs from the loaded topology. Enter jumps to and selects the match in the graph.
