# ADR 0015: C4 Diagrams Use Repo-Scoped Persistence

## Status

Accepted

## Context

C4 Diagrams are architectural visualizations of a codebase, generated by the AI through a hybrid process (tree-sitter structural extraction + AI semantic interpretation). The generation is expensive — it requires parsing the full codebase structure and burning AI tokens for interpretation.

Every other entity in the system (Issues, Whiteboards, Workspaces) is session-scoped with `session_id` FK and `ON DELETE CASCADE`. This works for entities that belong to a working session.

C4 Diagrams are different: they describe the **Repository**, not the Session. Multiple sessions working on the same repo should see the same diagram. Deleting a session should not destroy a diagram that took significant resources to generate.

## Decision

C4 Diagrams persist in a separate table keyed by `repo_path` (the absolute path to the repository), not by `session_id`. This makes them the first repo-scoped entity in the system.

- Any session whose working directory matches the `repo_path` can view the diagram.
- Deleting a session has no effect on diagrams.
- Diagram management (list, delete, rename) is handled through the C4 Diagram Panel UI.
- Generation is the only MCP operation; management does not require AI involvement.

## Consequences

- **Positive:** Diagrams survive session deletion and are shared across sessions. No wasted tokens rebuilding.
- **Positive:** Natural ownership model — diagrams belong to the codebase they describe.
- **Negative:** Introduces a new persistence pattern. Future repo-scoped entities will need to follow this precedent.
- **Negative:** `repo_path` as a key means diagrams are tied to a filesystem location. Moving a repo breaks the link. A hash of the path or a git remote URL could be considered later.
- **Negative:** No cascade cleanup when a repo is deleted from disk. Orphan diagrams may accumulate and need manual management.
