# PRD: Code Intelligence MCP & C4 Diagram Visualization

## Problem Statement

When an AI agent works on a software project, it lacks deep understanding of the codebase. It relies on the user to guide it through files, explain architecture, and point out relevant code. This wastes the user's time on orientation rather than building, and leads to the AI and user having different mental models of the codebase — the AI sees fragments through grep/glob while the user holds an architectural picture in their head.

The user needs a way to give the AI (and themselves) a shared, persistent understanding of the codebase: structural knowledge of symbols and dependencies, semantic search for finding code by intent, git history for understanding change context, and a visual architectural map they can both reference.

## Solution

Two integrated features:

1. **Code Intelligence MCP Tools** — A set of MCP tools that give the AI IDE-level code understanding: symbol navigation, semantic search, git history, and ownership signals. The underlying index is repo-scoped and persists across sessions, so new sessions skip re-indexing.

2. **C4 Diagram Panel** — A new panel type that renders a C4 architecture diagram of the codebase with drill-down navigation through four levels (Context, Container, Component, Code). The diagram is generated by the AI via MCP using a hybrid approach (tree-sitter structural extraction + AI semantic interpretation), persists across sessions, and includes inline code snippets at the Code level.

## User Stories

1. As a developer, I want the AI to search my codebase by semantic intent (e.g., "find authentication handling"), so that it can locate relevant code without exact text matching.
2. As a developer, I want the AI to search my codebase by keyword and regex, so that it can find exact matches quickly.
3. As a developer, I want the AI to go to the definition of a symbol, so that it can navigate directly to where something is defined.
4. As a developer, I want the AI to find all references to a symbol, so that it can understand the impact of changing that symbol.
5. As a developer, I want the AI to trace callers and callees of a function, so that it can understand execution flow and dependency chains.
6. As a developer, I want the AI to list repositories and map directory structures, so that it can orient itself in the codebase without guessing paths.
7. As a developer, I want the AI to pull exact file ranges, so that it can read specific code sections without loading entire files.
8. As a developer, I want the AI to search git commit history, so that it can understand what changed and why.
9. As a developer, I want the AI to search and compare diffs across revisions, so that it can recover intent from change history.
10. As a developer, I want the AI to see file ownership signals (CODEOWNERS, git blame), so that it knows who maintains which modules.
11. As a developer, I want the code intelligence index to persist across sessions, so that I don't waste time re-indexing when starting a new session in the same repo.
12. As a developer, I want the index to update incrementally (only changed files), so that re-indexing is fast after small changes.
13. As a developer, I want vector embeddings to regenerate on demand, so that I can refresh semantic search when the codebase changes significantly.
14. As a developer, I want to generate a C4 diagram of my codebase via the AI, so that I can visualize the architecture at multiple abstraction levels.
15. As a developer, I want to scope C4 diagram generation to a specific path or module, so that I can focus on a subsystem without generating noise from the full codebase.
16. As a developer, I want to control the depth of C4 diagram generation (Context, Container, Component, Code), so that I can get a quick overview or a detailed breakdown depending on my needs.
17. As a developer, I want to drill down through C4 levels by clicking on components, so that I can navigate from high-level system context to specific code.
18. As a developer, I want to see inline code snippets at the Code level (L4) of the C4 diagram, so that I can read actual code without leaving the visualization.
19. As a developer, I want the C4 diagram to persist across sessions, so that I don't waste tokens regenerating it every time.
20. As a developer, I want a zero state in the C4 Diagram Panel with a copy-paste prompt, so that I know how to get started with diagram generation.
21. As a developer, I want to list my saved C4 diagrams, so that I can find and open previously generated diagrams.
22. As a developer, I want to delete stale C4 diagrams, so that I can keep my diagram list clean.
23. As a developer, I want to rename C4 diagrams, so that I can organize them by purpose or date.
24. As a developer, I want the AI and I to see the same C4 diagram, so that we share a common understanding of the codebase architecture.
25. As a developer, I want the C4 diagram to show external actors (users, external systems) at the Context level, so that I can understand the system's boundaries.
26. As a developer, I want the C4 diagram to show containers (apps, databases, services) at the Container level, so that I can see the high-level technical architecture.
27. As a developer, I want the C4 diagram to show components (modules, packages, key classes) at the Component level, so that I can understand internal structure.
28. As a developer, I want the AI to ask me clarifying questions during C4 diagram generation (e.g., scope, focus areas), so that the resulting diagram matches my intent.
29. As a developer, I want the C4 diagram generation to use tree-sitter for structural extraction and AI for semantic labeling, so that the diagram is both accurate and meaningful.
30. As a developer, I want the code intelligence tools to work within my session's working directory, so that they answer questions about the repo I'm currently working on.

## Implementation Decisions

### Architecture

- **Repo-scoped persistence**: Code Intelligence Index, Vector Store, and C4 Diagrams are all keyed by `repo_path`, not `session_id`. This is the first repo-scoped entity pattern in the system. See ADR 0015.
- **Separate tables**: Index, Vector Store, and C4 Diagrams each get their own SQLite table. They have different lifecycles — index auto-updates, vectors regenerate on demand, diagrams are user-initiated.
- **Hybrid staleness**: Index uses content fingerprints for incremental updates (only changed files re-indexed). Vectors regenerate on demand. Diagrams regenerate on demand.
- **MCP for generation, UI for management**: The AI generates C4 diagrams via MCP. Users manage diagrams (list, delete, rename) through the panel UI.

### Modules to Build

- **Code Intelligence Index crate** — Tree-sitter parsing, symbol extraction, incremental update logic. New crate under `crates/`. Testable in isolation with real source files.
- **Code Intelligence Vector Store crate** — Embedding generation, similarity search. New crate under `crates/`. Thin wrapper around an embedding model.
- **Code Intelligence MCP Tools** — New tools added to `McpHandler` in `crates/mcp/`. Tools query the index, vector store, and git operations.
- **C4 Diagram Generator** — Hybrid pipeline: tree-sitter structural extraction → AI semantic interpretation → C4 data structure. Lives in the code intelligence crate.
- **C4 Diagram Repository** — SQLite CRUD for diagrams, keyed by `repo_path`. Follows the existing repository pattern in `crates/core/src/repositories/`.
- **C4 Diagram Panel** — New React panel component. Renders C4 levels with drill-down navigation, inline code snippets at L4, zero state with prompt. Registered in `panelRegistry.tsx`.
- **Database Schema** — New tables for `c4_diagrams`, `code_index`, `code_vectors`. Migration from schema v5 to v6.

### MCP Tool Set (v1)

- `search` — Semantic search across the codebase (vector store)
- `keyword_search` — Exact keyword/regex search (index + grep)
- `find_definition` — Go-to-definition for a symbol (index)
- `find_references` — Find all usages of a symbol (index)
- `find_callers` / `find_callees` — Call graph traversal (index)
- `list_files` — Directory structure and file listing (index)
- `read_file_range` — Pull exact file ranges (file I/O)
- `search_history` — Git commit search and diff queries (git)
- `blame` — File ownership via git blame (git)
- `generate_c4_diagram` — Generate a C4 diagram (hybrid pipeline)

### C4 Diagram Data Model

- A C4 Diagram contains Nodes, Edges, and Groups with C4 level metadata (`context`, `container`, `component`, `code`).
- Each element has a `level` field indicating which C4 level it belongs to.
- Code-level elements include an optional `code_snippet` field for inline display.
- The diagram is stored as a single JSON blob in the `c4_diagrams` table.

### C4 Panel Interaction

- **Zero state**: Shows a copy-paste prompt for the AI to generate a diagram.
- **Context level (L1)**: System boundary with external actors. Click a container to drill down.
- **Container level (L2)**: Apps, databases, services. Click a component to drill down.
- **Component level (L3)**: Modules, packages, key classes. Click a component to see code.
- **Code level (L4)**: Classes, functions with inline code snippets. Back button to navigate up.
- **Breadcrumb navigation**: Shows current path (e.g., `System > Auth Service > Token Validator`).

### Testing Decisions

- **Code Intelligence Index**: Test with real source files. Given a Rust/TS file, verify tree-sitter extracts correct symbols, definitions, references, and call graphs. Deterministic, no mocking needed.
- **C4 Diagram Repository**: Standard SQLite CRUD tests following the `issue_repository.rs` pattern — temp DB, create/read/update/delete, verify `repo_path` keying.
- **MCP tool integration**: Follow existing pattern in `crates/mcp-server/tests/integration_test.rs` — spawn binary, send JSON-RPC, verify tool discovery and responses.
- **Skip testing**: Vector store (external model dependency), C4 diagram generation AI interpretation (non-deterministic), panel rendering (manual verification).

## Out of Scope

- **Cross-service linking** (HTTP/gRPC route ↔ call-site matching) — deferred to v2
- **Runtime traces** (actual execution paths from production) — deferred to v2
- **Diagnostics** (linter errors, warnings, security issues) — deferred to v2
- **Refactoring tools** (rename, move, inline across files) — deferred to v2
- **Infra-as-code understanding** (Docker, K8s, Terraform) — deferred to v2
- **Similarity detection** (near-clone detection) — deferred to v2
- **Fresh documentation retrieval** (library/API docs) — deferred to v2
- **Live-updating C4 diagrams** — diagrams are one-shot snapshots, regenerated on demand
- **Cross-repo intelligence** — tools operate on the session's working directory repo only
- **CDC events for C4 diagram mutations** — not needed for v1, diagrams are static artifacts

## Further Notes

- The Code Intelligence Index is the foundation everything else builds on. Prioritize its implementation and testing.
- ADR 0015 documents the repo-scoped persistence decision.
- ADR 0003 planned several of these tools (`find_symbol`, `find_references`, `find_callers`/`callees`, `semantic_search`, `build_code_map`). This PRD extends that scope with history, ownership, and the C4 visualization layer.
- The `generate_c4_diagram` MCP tool replaces the old `build_code_map` concept from ADR 0003, which was designed to place Cards/Edges on the Visual Canvas. The new approach produces a read-only C4 diagram in a dedicated panel.
